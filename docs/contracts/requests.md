# Контракт первого среза заявок

Статус: реализованы хранение и публичный HTTP API, 2026-10-27.
Вход и сохранение смены статуса ещё не реализованы.
REST/JSON и goose согласованы в [решении об инструментах](../decisions/0003-frontend-migrations-api.md).
Бизнес-решения — в [плане](../plans/requests.md); технические детали ниже
описывают работающий публичный API; раздел админки — контракт следующего шага.

## Данные

Одна заявка содержит имя, телефон, необязательный комментарий, позиции,
сумму в RUB, статус и время создания. Позиция: ID товара, сохранённое название,
цена за штуку и целое положительное количество. Деньги — целые рубли:
PostgreSQL bigint, Go int64; JSON-значения ограничены безопасным целым JavaScript.
Проверять пределы до умножения и сложения, не использовать float для расчёта.

Каталог публикует SQL-представление catalog.request_products_v1:
product_id (UUID), name (text), unit_price_rub (bigint), is_available (boolean).
Сервис заявок имеет только SELECT на это представление и не читает внутренние
таблицы каталога. Созданы requests, request_items, request_submissions в схеме requests.
request_status_events, admin_users, admin_sessions появятся в следующих миграциях.
Runtime-роли разделены; DDL выполняет отдельная роль миграций.

## Публичное оформление

GET /api/products?limit=24&offset=0 возвращает объект items с доступными товарами:
id, name, unit_price_rub, available. limit — 1–100, offset — 0–100000.
GET /api/products/{id} возвращает один товар, в том числе недоступный;
невалидный UUID — 400, отсутствующий товар — 404. Полноценные фильтры ещё не добавлены.

POST /api/requests с заголовком Idempotency-Key (случайный UUID).
Тело: customer_name, phone, comment и items — массив объектов с product_id,
quantity, expected_unit_price_rub. Пустую корзину и повтор одного product_id
в массиве отклонять; frontend объединяет одинаковые товары в одну позицию.
Первичные технические пределы: 1–100 позиций, 1–10000 штук на позицию,
имя 1–100 символов, комментарий до 2000 символов. Цена/сумма — до 2^53−1.
Имя и комментарий обрезаются по краям; NUL и некорректный UTF-8 запрещены.
Телефон — '+' и 8–15 цифр с ненулевой первой цифрой; пробелы, скобки и дефисы
убираются. Национальное '8...' автоматически не превращается в '+7...'.
UUID приводятся к нижнему регистру, позиции сортируются по ID; перестановка
позиций и оформление телефона не меняют отпечаток нормализованного тела.
Эти ограничения проверяет слой хранения. HTTP принимает application/json,
не более 64 KiB, отклоняет неизвестные/повторные поля и нецелые числа.
Отсутствие quantity/expected_unit_price_rub не подменяется нулём.

Пример тела (контакты и UUID синтетические):

```json
{
  "customer_name": "Тестовый покупатель",
  "phone": "+79000000000",
  "comment": "Позвонить для уточнения",
  "items": [{
    "product_id": "11111111-1111-4111-8111-111111111111",
    "quantity": 2,
    "expected_unit_price_rub": 18000
  }]
}
```

Успех: {"request_id":"UUID","message":"Заявка получена"}. Ошибка:
{"error":{"code":"validation_error","message":"…"}}. Для price_changed
на верхнем уровне также возвращаются total_rub и items: product_id, name,
quantity, unit_price_rub. Цена подтверждается отдельной отправкой с новым ключом.
Неверный JSON — 400, чужой Origin — 403, тело больше лимита — 413,
неверный Content-Type — 415. Адрес Origin сверяется с APP_ORIGINS;
клиенты без Origin допускаются. Это не механизм аутентификации.

Каталог ограничивает работу с БД тремя секундами, создание — пятью, включая
ожидание пула и commit. HTTP-сервер ограничивает заголовки и время чтения/записи.
Создание допускает не более восьми одновременных обработчиков. Лимит по адресу
соединения: burst 30, восстановление одного запроса в секунду, до 1024 адресов
в памяти процесса. X-Forwarded-For не принимается на доверии: за Vite посетители
разделяют лимит proxy; политика доверенных proxy нужна перед production.
GET /healthz проверяет процесс, GET /readyz — подключение к БД (до секунды).

| Результат | Ответ |
|---|---|
| Заявка создана | 201, request_id и сообщение «Заявка получена» |
| Цена изменилась | 409 price_changed, актуальные цены и сумма; заявки нет |
| Товар недоступен | 409 product_unavailable; заявки нет |
| Ошибка полей/неизвестный товар | 422 validation_error; заявки нет |
| Ключ повторён с другим телом | 409 idempotency_conflict |
| Превышен лимит запросов | 429 |
| БД недоступна | 503; успешный приём не обещается |

Backend одной выборкой читает товары и проверяет доступность/цены. Позиции,
сумма и статус created сохраняются атомарно. Изменения каталога не переписывают
снимок заявки и не резервируют товар. После price_changed покупатель явно
подтверждает новые цены; frontend отправляет обновлённое тело с новым ключом.
«Купить сейчас» использует тот же API после ввода контактов и подтверждения.

Одинаковый ключ и нормализованное тело возвращают прежний завершённый результат,
включая исходный 201 или бизнес-конфликт, без создания второй заявки. Для ключа
хранятся отпечаток тела и результат; успешная запись фиксируется в одной транзакции
с заявкой. Конкурентные повторы сериализуются уникальностью ключа и транзакцией.
Реализовано INSERT ... ON CONFLICT DO NOTHING под READ COMMITTED: конфликтующий
INSERT ждёт завершения первой транзакции, следующий SELECT видит её результат.
Отпечаток — SHA-256 нормализованного тела; это сравнение содержимого, не защита
пароля. Невалидное тело/ключ отклоняется до транзакции. Завершённые бизнес-ошибки
цены, отсутствия/недоступности товара и границ суммы сохраняются с ключом.
Сетевой сбой/503 повторяется с тем же ключом и телом; после отката незавершённой
транзакции повтор может исполниться заново. Политику очистки ключей определить
отдельно; в первом срезе автоматического удаления нет.
Разные ключи обозначают самостоятельные заявки: совпадение телефона и состава
само по себе не повод автоматически объединять или отклонять их.

## Админка (ещё не реализована)

POST /api/admin/login, POST /api/admin/logout — пароль и серверная cookie-сессия
по [ADR](../decisions/0002-admin-auth.md), без MFA. Проверка сессии включает
активность сотрудника, отзыв и абсолютный срок 72 часа. Защита от CSRF нужна
также для входа/выхода. Процедуры создания и сброса пароля — административные,
без публичного API восстановления.

GET /api/admin/requests — список с пагинацией; GET /api/admin/requests/{id} —
состав и контакты. PATCH /api/admin/requests/{id}/status принимает status,
expected_version и cancellation_comment (обязателен при status=cancelled).
Отсутствующий, пустой или состоящий только из пробелов комментарий к отмене
возвращает 422 без изменения заявки. Это отдельное поле от комментария покупателя.
Версия предотвращает потерю изменений при работе в двух окнах:
устаревшая версия получает 409, изменение и событие истории сохраняются атомарно.
Нет сессии — 401, нет права admin — 403. Публичного чтения заявки по ID нет.

Согласованные переходы: created → delivery → delivered; из любого из этих трёх
статусов можно перейти в cancelled, в том числе после доставки.
cancelled — конечное состояние. Комментарий отмены сохраняется в событии истории
вместе с прежним/новым статусом, администратором и временем, атомарно со сменой
статуса. История доставки сохраняется; отмена не означает автоматический возврат
денег или изменение остатков.
Повтор текущего статуса с актуальной версией ничего не меняет; недопустимый
переход возвращает 409. Названия интерфейса: «Создано», «Доставка»,
«Доставлено», «Отменено». Исправление ошибочного конечного статуса требует
отдельного решения; скрытые обходы API не предусматривать.

## Проверка реализации

Проверить создание нескольких позиций, отсутствие копеек и переполнений,
откат всей заявки при ошибке, изменение цены с повторным подтверждением,
конкурентные повторы одного ключа, повтор после потери ответа, конфликт тела,
неизменность снимка, недоступность БД, запрет анонимного чтения/изменения,
отзыв/истечение сессии, CSRF, безопасный вывод комментария и конкурирующую
смену статуса. Проверить отмену из каждого разрешённого состояния, включая
delivered; отказ без комментария или с пробельным комментарием без изменений
в БД; атомарное сохранение комментария и автора в истории.
Нужны отдельные test DB/роли и синтетические данные.
