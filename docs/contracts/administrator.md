# API администратора

Пути начинаются с `/api/admin`. Браузер использует один origin.
`products` обслуживает каталог; остальные пути — заявки. Прямые обращения
к обоим backend проходят те же проверки, что запросы через frontend proxy.

## Сессия

- `POST /login`: `{username, password}` → `{username}` и cookie `tireshop_admin`.
- `GET /session`: `{username}` или 401; используется также каталогом.
- `POST /logout`: отзыв текущей сессии и удаление cookie.

POST/PUT требуют `Origin` из APP_ORIGINS, `X-Admin-Request: 1`, JSON.
Максимальный размер тела 64 KiB. Пароли, cookie и контакты в логи не пишутся.
Неверные credentials — 401, лимит попыток — 429, недоступная БД/auth — 503.

## Заявки

- `GET /requests?offset=0`: `{items: [...]}`, 50 записей, новые первыми.
- `GET /requests/{uuid}`: `{request, history}`. Последние 100 событий,
  новые первыми: `before`, `after`, `actor`, `comment`, `created_at`.
- `PUT /requests/{uuid}`: `{version, status, comment, items?}`.
  `items` — массив `{product_id, quantity}`, 1–100 уникальных товаров,
  количество 1–10000. Пропущенный/null items сохраняет состав; пустой запрещён.
  Передача items после выхода из created запрещена. Успех возвращает заявку.

Поля заявки: `id`, `customer_name`, `phone`, исходный `comment`, `status`,
`version`, `total_rub`, `created_at`, `items`. В списке items пуст,
в деталях позиции: `product_id`, `name`, `quantity`, `unit_price_rub`.
Комментарий PUT — запись сотрудника в истории, не замена покупательского.

Статусы и переходы сохранены из исходного плана. Повтор того же статуса
допустим для комментария/состава; отмена всегда требует комментария.
`created → delivery` списывает весь итоговый состав атомарно со статусом.
Нет частичной отправки, автоматического резерва или автоматического возврата.

## Каталог

Список поддерживает `kind=tyre|wheel`, `sort=<поле>` и `direction=asc|desc`.
Сортировка выполняется до пагинации; числовые значения сортируются как числа,
NULL — в конце, равные значения дополнительно упорядочиваются по UUID.
Допустимы name, unit_price_rub, stock, is_available и поля details из словаря;
неизвестное поле/направление возвращает 400. Без sort сохраняется порядок UUID.
В DTO добавлен `image_url` первой фотографии; клиент использует её миниатюру.
Настройки видимости колонок сохраняются frontend по логину в текущем браузере.

Уточнение 2026-10-28: товар возвращает объект `details` с характеристиками,
описанием, SKU, замечаниями и `units_per_sale`. Объект можно передать при
создании/изменении; если он пропущен, характеристики сохраняются.
У существующего товара units_per_sale неизменяемо: stock и цена выражены
в единицах продажи, включая комплект. Снимки позиций заявки дополнены
`unit_label`. Словарь — [импорт каталога](../decisions/0005-initial-catalog-import.md).

- `GET /products?offset=0`: `{items: [...]}`, 50 товаров, включая скрытые.
- `POST /products`: `{id, name, unit_price_rub, stock, available, version: 0}`.
  Клиент генерирует UUID один раз; повтор с тем же id возвращает 409,
  а не создаёт второй товар. Начальная версия сохранённого товара — 1.
- `PUT /products/{uuid}`: те же поля с ожидаемой текущей version.

Название 1–300 символов, цена и остаток — целые от 0 до 9007199254740991.
Все поля цены, доступности и остатка обязательны. `stock` — абсолютный текущий
остаток, `available` — видимость/доступность оформления, не расчёт из stock.
Оформление без резерва допускается при stock=0; отправить такую заявку
нельзя до пополнения. Скрытие заменяет физическое удаление в интерфейсе.

## Конфликты

409 `version_conflict` — запись изменена другим действием, включая списание.
409 `insufficient_stock` — весь переход отклонён, остатки и заявка прежние.
422 — неверный состав/поля/переход/комментарий; 404 — заявка не найдена.
При timeout/503 результат не определён: перечитать запись перед повтором.
Нельзя автоматически подставлять новую version под старую форму:
сотрудник должен проверить актуальное состояние.
