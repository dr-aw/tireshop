# Каталог и заявки: границы первой версии

Дата: 2026-10-22. Статус: принято по обсуждению с пользователем.

## Контекст

Первая версия принимает заявки для ручной обработки сотрудником. Оплаты,
резервирования и кабинета покупателя нет. Пользователю достаточно сообщения
«Заявка получена». Первым реализуется сквозной сценарий заявки и защищённой
админки; полноценная витрина следует за ним.

## Решение

Каталог — Go backend товаров, цен и правил их изменения. Он обслуживает API
витрины; интерфейс редактирования товаров является отдельным пользовательским
интерфейсом, а не определением сервиса каталога.

Заявки — отдельный Go backend создания тикетов и ручной обработки сотрудниками.
Он владеет заявками, позициями и статусами. Админка обращается к его защищённому
API. Оба сервиса запускаются независимо, frontend поставляется как статика.

На старте используется общая PostgreSQL. Только каталог изменяет товары;
только сервис заявок изменяет заявки. Для проверки цены сервис заявок читает
SQL-контракт каталога напрямую, без синхронного HTTP-вызова каталога.
Контракт реализуется отдельным представлением с минимальными полями товара
и правом SELECT для роли заявок. Права записи в товары ей не выдаются.
Конкретные поля и типы определяются после словаря данных, до миграций.
Миграции выполняются отдельной ролью, runtime-роли не получают DDL-права.

Это компромисс: изменения контракта БД требуют согласования между сервисами.
Представление позволяет сохранить контракт при части изменений внутренних
таблиц, но не устраняет связанность. Общая БД остаётся точкой отказа и конкуренции
за ресурсы. Удаление HTTP-вызова сокращает зависимости пути создания заявки;
падение процесса каталога само по себе не блокирует этот путь.

## Цена и создание заявки

Браузер передаёт идентификаторы, количество и показанные цены. Backend читает
цены и рассчитывает сумму самостоятельно. Если цена отличается, заявка не
создаётся: frontend показывает новую сумму и запрашивает подтверждение отправки.
Повторная отправка снова проверяется, даже если изменения цен редки.

Заявка и её позиции сохраняются атомарно с названиями, ценами и количеством
на момент проверки. Последующие изменения товара не меняют заявку.
Транзакция не остаётся открытой, пока человек подтверждает новую сумму.
Сохраняемая цена — снимок, прочитанный при проверке, а не обещание блокировать
все параллельные изменения цены до COMMIT. Оплаты и резерва эта операция не создаёт.

Повтор сетевого запроса должен возвращать прежний результат, а не второй тикет.
Детали ключа идемпотентности и его поведения при изменении цены, а также правила
для похожих, но самостоятельных заявок определяются в плане реализации.

## Порядок и открытые вопросы

Первый срез использует синтетические товары и включает форму, сохранение,
защищённый список/детали и ручную смену статуса. Полная витрина и реальные фото
не являются зависимостью этого среза. Каталог остаётся частью первой версии.

Телефон, Telegram и Max — альтернативные каналы связи, без интеграции ботов.
Реальные контакты требуют подтверждения; значения из макетов не публикуются
автоматически. После отправки выводится «Заявка получена» без обещания оплаты
или резервирования.

Уточнение 2026-10-22: валюта всегда RUB, цены и суммы выражаются целыми рублями,
без копеек. Пользователь подтвердил корзину и «Купить сейчас» и затем уточнил:
на всю корзину создаётся одна заявка, содержащая одну или несколько позиций.
Цена задаётся за одну шину/диск, количество — целое положительное число штук.
Список и статусы доступны только администратору, покупатель статус не видит.
Статусы: «Создано», «Доставка», «Доставлено», «Отменено». Оформление корзины
и «Купить сейчас» требуют контактов покупателя и явного подтверждения отправки.
Защита админки принята в [отдельном ADR](0002-admin-auth.md).

До реализации уточнить переходы статусов, тип хранения целых сумм
и SQL-контракт. Выбор frontend,
инструмента миграций и точного API ещё не сделан. Актуальные вопросы и критерии —
в [плане заявок](../plans/requests.md).
