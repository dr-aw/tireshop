# Собственный вход в админку и сессии в PostgreSQL

Дата: 2026-10-22. Статус: принято пользователем; реализация не начата.

## Контекст

Заявки читает и обрабатывает только администратор. Покупателю не нужны
регистрация и личный кабинет. Пользователь выбрал собственный вход без готового
провайдера идентификации и принял зависимость админки от общей PostgreSQL.

## Решение

- Учётные записи сотрудников создаются явно, публичной регистрации нет.
  Пароли хранятся как Argon2id-хеши с уникальной солью. По уточнению пользователя
  MFA исключена из первой версии; вход выполняется по логину и паролю.
- Серверные сессии хранятся в общей PostgreSQL. Браузер получает случайный
  непрозрачный идентификатор в Secure/HttpOnly/SameSite cookie.
  Начальный срок — 72 часа от успешного входа, без автоматического продления
  активностью; выход или блокировка отзывают сессию раньше.
- Восстановление выполняет вручную технический администратор с доступом к БД.
  Публичного восстановления нет. Процедура должна отзывать старые сессии
  и безопасно заменять данные входа; пароль в открытом виде в БД не записывается.
- Сервис заявок владеет данными сотрудников и сессий для своей админки;
  runtime-роль каталога не получает к ним доступ. Миграции выполняет отдельная роль.
- Backend проверяет действительность сессии и право admin на каждом защищённом
  запросе; доступ по умолчанию запрещён. Нужны HTTPS, CSRF-защита изменений,
  ограничение попыток входа, сроки сессий и отзыв при выходе/блокировке.
- Собственная реализация использует проверенные криптографические библиотеки.
  Отдельные сервис/БД аутентификации, Redis, JWT и OIDC-провайдер не вводятся.

## Последствия

PostgreSQL остаётся общей точкой отказа. Без соединения нельзя завершить вход,
проверить существующую сессию или работать с заявками. Защищённые операции
возвращают ошибку временной недоступности; отказ БД не разрешает обход проверки.
Статическая оболочка админки при этом может открываться.

Выделение только сессий в другое хранилище не обеспечит работоспособность
обработки заявок при отказе их БД. На текущем этапе принимаем эту зависимость
и избегаем дополнительной инфраструктуры. Сессии проверяются по идентификатору;
конкретные индексы, очистка истёкших записей и лимиты соединений задаются
при проектировании схемы и запросов.

## Оставшиеся детали и проверка

До реализации описать создание первой учётной записи и процедуру ручного
восстановления доступа.
Контракт сессий должен предусматривать
безопасное хранение идентификаторов на сервере, их обновление при входе и отзыв.

Проверить вход по паролю, запрет прямых анонимных API-запросов, истечение и отзыв
сессий, CSRF-защиту, блокировку сотрудника и отказ БД без предоставления доступа.
План реализации — [заявки и админка](../plans/requests.md).
