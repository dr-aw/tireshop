# Инструменты первого среза: интерфейс, миграции и HTTP API

Обновлено: 2026-10-27. Goose, REST/JSON и React + TypeScript + Vite приняты
для первого среза. Реализованы миграции, HTTP API и первая форма; дальнейшие
страницы каталога и админка остаются в плане.

## Интерфейс: почему рассматриваем React

TypeScript — язык, DOM — дерево элементов страницы в браузере, React — библиотека
построения интерфейса из компонентов. Vite обеспечивает разработку и сборку
статических файлов. Ни React, ни Vite не задают дизайн: ориентиры — материалы
из .local и согласованный сайт конкурента. HTML/CSS и основы JS нужны при любом выборе.

Ручное изменение DOM подходит для небольшого количества независимых действий.
Оно позволяет обойтись без runtime React, сократить загружаемый JS и избежать
его работы по вычислению обновлений. Это не гарантия скорости всего магазина:
изображения, сеть, объём DOM и организация обновлений могут влиять сильнее.
Сравнения производительности в проекте пока не проводились.

Наш интерфейс должен согласовывать связанные состояния: количество и сумма
корзины, индикатор корзины в шапке, поля формы, отправка, ошибка сети,
подтверждение изменившейся цены, фильтры и статусы админки. При прямом DOM
нужно самим обновлять каждое зависимое место и не оставлять устаревшие значения.
React позволяет описывать отображение через состояние; обработчик меняет данные,
а библиотека согласовывает представление. Это уменьшает ручную синхронизацию,
но добавляет зависимость, загрузку JS и понятия props/state/render/hooks.

Решение: React + TypeScript + Vite для первого интерактивного среза.
Обычный CSS, fetch и локальное состояние компонентов; без Redux, собственного
дизайн-фреймворка и отдельного Node-сервера в runtime. Суммы, которые выводятся
из количества и цен, вычислять, а не хранить вторую копию в state.
React не заменяет серверную проверку данных и прав.

Статическая доставка не требует превратить все страницы в клиентскую SPA.
Для информационных страниц достаточно HTML; перед полноценным каталогом
нужно решить начальную HTML-выдачу/предгенерацию карточек для поиска и предпросмотра
ссылок. Один пустой HTML с загрузкой всего каталога через JS не принимается
автоматически как итоговая архитектура витрины.

До приёмки измерять загрузку и отклик на реалистичном каталоге, проверять размер
JS, изображения и работу на мобильном устройстве. Выбор React сам по себе
не доказывает ни быстродействие, ни его отсутствие.

Основания: [Thinking in React](https://react.dev/learn/thinking-in-react),
[вычисляемые данные и эффекты](https://react.dev/learn/you-might-not-need-an-effect),
[сборка Vite](https://vite.dev/guide/).

## Миграции: goose и явные SQL-файлы

Решение: изменения схемы PostgreSQL хранятся в версионированных SQL-файлах
и применяются goose. ORM не требуется. Каждый сервис имеет собственный каталог
миграций и таблицу версий в своей схеме; migrations каталога публикуют SQL-контракт,
после этого migrations заявок настраивают доступ к нему. Изменения выполняются
отдельной административной командой под ролью миграций, а не каждой копией API
при запуске. Runtime-роли не получают права изменения схемы.

Goose хранит в БД историю применённых миграций. Файл в Git описывает переход
схемы, запись в таблице версий — факт его применения к конкретной БД.
Обычная SQL-миграция goose выполняется в транзакции; специальные операции,
не допускающие транзакцию, требуют отдельного разбора и явной настройки.
Нельзя предполагать, что вся пачка файлов выполняется одной транзакцией.

Цикл работы: написать новую миграцию → проверить SQL и права → применить к
отдельной test DB → проверить ограничения и запросы → проверить обновление
с предыдущей версии с синтетическими данными → применить к dev DB.
Повторный up не должен повторять уже применённые файлы. Проверять и пустую БД,
и обновление существующей: это разные сценарии.

Применённые миграции не редактировать. Исправление — новая миграция.
Down — явно написанное обратное изменение, а не восстановление данных:
DROP TABLE уничтожает строки. Для обычного исправления предпочтительно новое
изменение вперёд; rollback приложения также требует совместимой схемы.
Удаление/переименование используемых полей планируется поэтапно: добавить новое,
перевести код и данные, затем удалить старое.

Первичная настройка служебных ролей/доступа выполняется отдельно от runtime.
Команды db:bootstrap, db:migrate и db:runtime описаны в README. Пароли не помещать
в SQL-файлы или аргументы CLI; goose закреплён в mise.toml/mise.lock.

Основания: [команды goose](https://pressly.github.io/goose/documentation/cli-commands/),
[аннотации и транзакции](https://pressly.github.io/goose/documentation/annotations/).

## API: REST с JSON

Решение: браузер обращается к Go backend через ресурсный HTTP API с JSON.
Это соответствует формам, спискам и смене статусов; GraphQL и gRPC для первого
среза не нужны. Go обрабатывает валидацию, права, цены и транзакции; TypeScript
обеспечивает взаимодействие и отображение. Статические типы TS не проверяют
входящий JSON во время выполнения и не заменяют серверную валидацию.

Контракт задаёт методы, пути, обязательные поля, ограничения, ответы и ошибки.
REST не определяет автоматически правила повторной отправки и изменения цены.
Для них в [контракте заявок](../contracts/requests.md) предусмотрены ключ повторной
отправки, 409 при конфликте и проверка версии при смене статуса.
Серверная cookie-сессия остаётся принятой схемой входа; слово REST здесь означает
практический стиль HTTP API, а не заявление о выполнении всех ограничений REST.

Формат ошибки: объект error с code и message. Frontend различает сценарии
по code, не разбирает текст сообщения. Реализованный публичный HTTP-контракт
с примерами и лимитами описан в docs/contracts/requests.md; админские маршруты
там пока проектируются. Отдельной OpenAPI-спецификации пока нет.

## Вопросы для разбора на примерах

1. Количество товара изменилось. Где хранить сумму корзины: отдельным состоянием
   или вычислять из позиций? Какие ошибки создаёт второй источник значения?
2. Клиент получил timeout, но заявка уже записалась в БД. Что случится при повторе
   POST без ключа, а что должно случиться с тем же ключом?
3. Миграция добавляет обязательное поле в таблицу с существующими строками.
   Откуда возьмутся значения для этих строк и как сохранить совместимость кода?

Вопросы учебные, не блокируют подготовку каркаса. Перед первой настоящей миграцией
разобрать её SQL, права, блокировки, поведение при ошибке и проверку результата.
