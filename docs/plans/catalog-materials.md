# Материалы, каталог, дизайн и фотографии

Статус: план от 2026-10-17. Реализация не начата. Основной roadmap —
[PLANS.md](../../PLANS.md); постоянные правила — [AGENTS.md](../../AGENTS.md).

## Цель и границы

Подготовить предоставленные заказчиком материалы для каталога грузовых шин
и дисков и заявок без онлайн-оплаты. HTML задаёт примерное направление дизайна;
разрешено менять frontend, структуру компонентов и визуальные решения.
Сайт конкурента используется как источник функциональных идей.
Архитектурные решения о сервисах и статическом frontend сохраняются.
Пока выполняются анализ и планирование; не запускать разработку приложения,
массовое преобразование изображений или регулярный импорт по этому документу
без следующей задачи пользователя на реализацию.

## Хранение и доступ

- `.local/` исключена пользователем из Git. По его указанию `.dockerignore`
  оставлен без изменения. Данные доступны контейнеру через bind mount;
  исключения build context не управляют доступом через mounts.
- Сохранять исходники неизменными; производные данные/фото размещать отдельно,
  например `.local/derived/`, отчёты с исходными значениями — `.local/reports/`.
- В публичный Git включать словарь полей, спецификации, код преобразований
  и синтетические fixtures. Публикацию реальных изображений и описаний на сайте
  согласовать как часть подготовки каталога; приватные исходники не нужны CI.
- Агентам давать нужные исходники через отдельный read-only mount `/inputs`.
  `.gitignore` сам по себе не запрещает агенту читать файл. Полный workspace mount
  с `.local` внутри не обеспечивает read-only для оригиналов: при настройке
  предусмотреть отдельную рабочую копию без `.local` или отдельное перекрывающее
  read-only монтирование. Игнорируемые данные не переносятся в worktrees автоматически.
- На обычную задачу передавать конкретные файлы и вопрос, а не все фото/таблицы
  в контекст модели. Для разработки без оригиналов должны работать fixtures.

## Подготовка данных

1. В контейнере создать повторяемый аудит XLSX: учитывать только строки товаров,
   исключать сводки/пустые строки, проверять уникальность SKU, типы, диапазоны,
   пустые поля, ссылки на фото. Вывод — отчёт, без исправления оригиналов.
2. Составить словарь полей и модель двух типов товара:
   - общие: SKU, тип, название, описание, цена/валюта, единица продажи,
     доступное количество, фотографии;
   - шины: бренд, модель, год, исходный размер, ширина/профиль/диаметр,
     сезонность, остаток протектора, индексы нагрузки/скорости, ось при наличии;
   - диски: диаметр, ширина, ET, PCD (число отверстий и диаметр окружности),
     DIA, тип/состояние, дисков в комплекте и число комплектов.
3. Разделить количество на складе и остаток протектора: колонка «Остаток»
   у шин содержит проценты согласно описаниям, не складской остаток.
   Зафиксировать это в словаре. Для дисков определить цену за штуку/комплект.
4. Поддержать метрические и дюймовые размеры (`295/80R22.5`, `11R22.5`):
   не считать `11` миллиметрами и не придумывать отсутствующий профиль.
   Геометрию типоразмера не подменять транспортными габаритами/массой для ТК.
5. Не извлекать автоматически достоверные свойства из рекламного текста:
   ось, страна, дефекты, масса и гарантии могут отсутствовать либо конфликтовать.
   Неизвестные значения хранить как неизвестные; спорные вынести в отчёт.
6. Согласовать первоначальное наполнение: проверенная нормализованная выгрузка
   и повторяемая загрузка через владельца данных каталога, с dry-run и отчётом.
   Это ограниченная подготовка начального каталога, без панели регулярного импорта,
   очередей и автоматической синхронизации поставщиков. Будущий импортер остаётся
   отдельным асинхронным сервисом согласно AGENTS.md.

Уже замеченные примеры для отчёта, не автоматические исправления:

- У SU-1702 список фото содержит `SU-1703-03.jpg`, в папке лежит `SU-1702-03.jpg`.
- В папке SU-1904 есть файлы `SN-1904-*.jpg.jpg`: проверить соответствие SKU
  и не связывать снимки по приблизительному совпадению без подтверждения.
- HTML предлагает PCD `6x222.5`, XLSX содержит `6x222.25`: данные макета
  не должны становиться источником технических характеристик.
- Ранний PRD предлагает email/мессенджер и импорт; текущий roadmap предусматривает
  защищённую админку заявок и откладывает регулярные интеграции.
- В материалах различаются обещанные сроки доставки; телефоны, адреса, цены,
  гарантии и способы оплаты макетов считать примерами до подтверждения заказчиком.

Готовность: утверждены словарь, единицы продажи и правила неизвестных значений;
каждый SKU либо валиден, либо имеет объяснимую ошибку; проверены ссылки на фото;
повторная первоначальная загрузка не создаёт дубли; синтетический пример работает в CI.

## Дизайн и функциональность

Ориентир заказчика: светлая основа, красные акценты (в HTML часто `#e31e24`),
крупные фотографии состояния, заметные размер/цена/остаток, простая заявка.
Не требуется пиксельное воспроизведение. HTML — референс, качество его кода
и примерные данные не являются обязательными для новой реализации.

Перед реализацией:

1. Просмотреть главную, каталог и карточку в браузере на desktop/mobile.
2. Подготовить согласованный набор компонентов, типографику, состояния и навигацию.
3. Для каталога спроектировать переключение шин/дисков и применимые фильтры:
   у диска нет остатка протектора, у шины нет ET/PCD. Значения фильтров брать
   из реальных нормализованных данных, а не из статических опций HTML.
4. Предусмотреть поиск по SKU/названию/размеру, сортировку, сброс фильтров,
   пустую выдачу, загрузку/ошибку, отсутствие фото/цены/наличия, пагинацию.
   Предлагаемое поведение: фильтры/сортировка/страница в URL для ссылки и Back;
   изменение фильтра сбрасывает страницу. Решение frontend/backend — на этапе 2.
5. Карточка: галерея, достоверные характеристики, единица цены и комплектация,
   наличие, форма заявки с выбранным SKU. Проработать клавиатуру, подписи полей,
   focus, контраст и мобильные фильтры. Не добавлять оплату из текста макета.
6. Для статического frontend отдельно решить прямое открытие URL товара,
   метаданные/индексацию и сборку страниц; выбор framework пока открыт.

### Функциональный референс конкурента

Источник: <https://integral178.ru/catalog/gruzovye-shiny?page=2>, просмотр HTML 2026-10-17.
Web-инструмент не открыл URL, но прямой HTTP-запрос получил HTML (~308 KB).
Интерактивное поведение и корректность фильтров кликами не проверены.

В разметке видны поиск, фильтры бренда/сезона/оси/диаметра, наличие, сортировка
по новизне/цене, счётчик выдачи, карточки с размером/ценой и переходом к деталям,
навигация по каталогу и тематические подборки. Для MVP взять за ориентир
поиск/фильтры/сортировку/понятную карточку. Подборки, калькулятор, блог и услуги
рассматривать позднее; они не добавлены в обязательный объём.
Дизайн, код, фотографии, описания товаров и коммерческие обещания конкурента
не переносить. Свой список проверок URL/Back/mobile — проектное предложение,
а не утверждение о проверенном поведении конкурента.

Готовность: согласованы три основных экрана и мобильные состояния;
заявка доступна из карточки; не используются неподтверждённые контакты/обещания;
фильтры работают на синтетических данных обоих типов.

## Фотографии: отдельная задача после согласования пилота

Рабочий целевой формат — **WebP** (трактовка голосового пожелания «в пи»).
Качество, фон и размеры ниже — предложения для пилота, не окончательные требования.

1. Аудит: декодируемость, реальные размеры/формат, EXIF orientation, дубликаты,
   связь SKU → снимки, пропущенные файлы и лишние изображения.
2. Создать manifest: SKU, оригинальный путь, checksum оригинала, порядок,
   обложка, производные пути/размеры, версия настроек обработки.
3. Пилот на 5–10 товарах обоих типов: поворот по EXIF, приведение в sRGB,
   WebP и несколько размеров (например 320/640/1280 px, без увеличения оригинала).
   Для карточек предложить квадратную область с `contain` и единым фоном;
   детали галереи сохраняют полный кадр. Не обрезать маркировку и дефекты.
4. Удалять ненужные метаданные из производных. Не ретушировать состояние товара,
   не генерировать детали, не менять протектор/маркировку. Удаление фона
   рассматривать отдельно только после оценки пилота.
5. Выбрать качество по визуальному сравнению и весу; не фиксировать процент
   сжатия до измерений. Проверить читаемость маркировки и видимость дефектов.
6. После принятия пилота выполнить пакетную обработку в контейнере.
   Оригиналы неизменны; повторный запуск с теми же входами/настройками стабилен,
   ошибки отдельных файлов отражены в отчёте. Производные публиковать отдельным
   шагом в выбранное хранилище статики/медиа; MinIO заранее не требуется.
7. На frontend задать размеры изображений, responsive sources и lazy loading
   для изображений ниже первого экрана; проверить отсутствие скачков разметки.

Готовность: каждый опубликованный снимок сопоставлен SKU; выбранные обложки
проверены; нет потерянных важных деталей; исходники сохранены; параметры,
результат сравнения и размеры производных зафиксированы.
