# Клиентский подбор каталога к 1.0

Дата: 2026-11-10. Статус: реализовано и проверено локально. Production rollout не выполнялся.
Основной этап — [PLANS.md](../../PLANS.md).

## Результат и границы

Мобильный подбор следует `.local/v2/Каталог.pdf`: категории, плитки диаметров
со счётчиками, список размеров выбранного диаметра. PDF просмотрен визуально;
пример показывает R17.5 и размеры 195/70R17.5, 205/60R17.5 и другие.
Примеры и числа из макета не становятся данными каталога. PDF остаётся вне Git.

Над «Шины»/«Диски» — более тонкая кнопка «Все товары» на всю ширину.
Она активна по умолчанию на `/` без категории. Прямая ссылка на категорию
или сохранённый подбор восстанавливает выбранное состояние.
Существующие меню, карточки, корзина, заявки и тема сохраняются.
Админка не получает новый дизайн; её фильтры и редактирование продолжают работать.

Подтверждено пользователем:

- «шт» — суммарный физический остаток `stock × units_per_sale`, а не число карточек.
- Диски: после диаметра размер по ширине (например, 6.75×17.5), дополнительно
  PCD, ET и DIA. Одинаковые ширина/диаметр не означают совместимость крепления.

Остальные технические решения ниже — предлагаемый путь реализации.
Каталог остаётся владельцем данных и одним сервисом. Новый сервис, Redis,
материализованные справочники и изменения сервиса заявок не требуются.

## Что уже есть

- Миграция `00004_typed_specs.sql` разделила `catalog.tyre_specs` и
  `catalog.wheel_specs`; общие данные и stock находятся в `catalog.products`.
- У шин исходный `size` определяет generated-поля ширины, профиля и
  `rim_diameter_inches`. У дисков уже есть `diameter_inches` и `width_inches`.
- `catalog.product_details` предоставляет общую проекцию. API фильтрует
  `size`, `rim_diameter`, `diameter`, `width` и другие характеристики.
- Справочники `/api/products/filters` и `/api/admin/products/filters`
  зависят только от категории/доступа. Сейчас Go получает подходящие строки
  товаров и сам собирает уникальные значения, без счётчиков и зависимости размеров.
- `frontend/src/catalog-filters.tsx` используется витриной и админкой;
  общая очистка параметров влияет также на URL витрины.
- Специальных индексов по диаметру/размеру пока нет; PK/unique по товарам,
  артикулу и фотографиям не заменяют индексы под новый подбор.

Это выводы из кода и миграций, не новый аудит содержимого работающей БД.
Перед миграцией нужен отдельный локальный аудит заполненности и форматов.

## UX и состояние подбора

1. «Все товары»: смешанная выдача, существующие общие цена/наличие и сортировка.
   Размерные блоки отсутствуют; переход сюда очищает категорийные параметры.
2. «Шины»/«Диски»: один выбранный тип, плитки диаметров в числовом порядке.
   Изначально диаметр не выбран, выдаются все товары категории.
3. Выбор диаметра сразу обновляет выдачу и открывает размеры этого диаметра.
   Повторный клик снимает диаметр и размер. Смена диаметра сбрасывает размер.
4. Выбор одного размера сразу уточняет выдачу; повторный клик снимает размер.
   Множественный выбор в 1.0 не включать. У шин подпись — полный типоразмер;
   у дисков — ширина × диаметр, фильтрация по двум числовым полям.
5. Смена категории очищает диаметр, размер и несовместимые характеристики;
   общие цена/наличие/сортировка сохраняются. Любое изменение сбрасывает страницу.
6. Уточнение пользователя при реализации: из прежних полей оставить цену и
   наличие, у дисков также согласованные PCD/ET/DIA. Бренд, модель, год, сезон,
   состояние, протектор, индексы нагрузки/скорости, отдельные ширина/профиль шины
   и тип диска убрать только из userspace. Эти старые URL-параметры больше
   не влияют на клиентскую выдачу. Поиск и сортировка сохраняются.
   Legacy size и эквиваленты диаметра сохраняют совместимость с новым подбором;
   неотображаемый исходный размер показывать как снимаемое ограничение.
7. На мобильном плитки и строки размеров соответствуют PDF, адаптируются к
   ширине 320–430 px. Список размеров может прокручиваться, но выбранный пункт
   и выдача должны быть доступны, нижнее меню не перекрывает кнопки.
   На ПК тот же подбор помещается в существующую боковую область.

Размеры и радиусы берутся из БД, без жёстко заданного набора R13…R22.5.
Термин API/БД `radius` используется по запросу пользователя; значение 17.5 —
посадочный **диаметр в дюймах**, не геометрический радиус. В UI — «Диаметр, R».

URL хранит применённый подбор; reload, Back/Forward и ссылки на категории
восстанавливают его. Запросы отменяются при смене выбора; поздний ответ не
перезаписывает новое состояние. При ошибке доступны повтор и сброс, ошибка
не выглядит как нулевой остаток. Кнопки имеют доступные подписи, состояние
выбора и фокус; проверить клавиатуру, светлую/тёмную тему и reduced-motion.

## Данные и миграция

Добавить новую миграцию после 00004, старые миграции не редактировать.
Сохранить текущие источники редактирования и совместимость старого backend.

| Таблица | Новое поле | Источник |
| --- | --- | --- |
| `tyre_specs` | `radius numeric GENERATED … STORED` | Прямой разбор исходного `size` той же функцией, что и `rim_diameter_inches` |
| `tyre_specs` | `size_key text GENERATED … STORED` | Канонический полный распознанный размер из `size` |
| `wheel_specs` | `radius numeric GENERATED … STORED` | `diameter_inches` |

Generated-выражение шины не ссылается на другое generated-поле: напрямую
вызывает разбор `size`. Так `radius` не становится независимым ручным значением,
а нынешние admin/import Save автоматически обновляют его. Избыточность двух
числовых полей шин — сознательная плата за запрошенное имя и совместимость;
в проверках требовать их равенство, включая NULL.

Использовать точный numeric без округления до целого/одного знака. Входные числа
конечные, положительные и в документированных пределах; десятичные значения
R17.5, R19.5, R22.5 не теряются. В API передавать 17.5, префикс R только в UI.

`size` шины остаётся исходной строкой. `size_key` объединяет эквивалентные
написания: пробелы, регистр R, запятая/точка, незначащие конечные нули.
Например, `195/70 r17,5` и `195/70R17.50` дают `195/70R17.5`.
Не подменять дюймовые размеры метрическими и не додумывать отсутствующий профиль.
Проверить 165R13, 11R22.5, 7.50R16; формат подписи выбрать детерминированно.
Нераспознанные строки сохраняются, производные значения NULL; не извлекать
размер из названия. Такие товары доступны в категории/поиске, но не получают
выдуманный диаметр. Для дисков размер определяется `(radius, width_inches)`;
маркировка и PCD/ET/DIA остаются отдельными характеристиками.

Отдельная таблица радиусов и many-to-many связей с размерами не требуется:
размер шины однозначно задаёт диаметр, товары уже задают существующие сочетания.
Справочник потребуется, если появится отдельное управление допустимыми размерами
независимо от наличия товаров; в текущую задачу это не входит.

Добавлять новые столбцы проекции в конец, сохранить прежние имена/типы и права.
Предусмотреть новую версионированную функцию канонизации; не менять молча
immutable-функцию, на которую уже опираются сохранённые generated-значения.
UUID, версии товаров, цены, stock, фото, заявки и исходные размеры сохраняются.
Составить отчёт неизвестных размеров и коллизий нормализации до применения.

## API и совместимость

Существующие list endpoints и `/filters` сохраняют контракт и старые параметры.
Общий SQL builder/валидацию расширить, не создавать второй механизм выдачи товаров.
Новый frontend-компонент отделить от `CatalogFilters` админки; переиспользовать
чистые утилиты, но не менять её очистку/набор полей как побочный эффект.

Предлагаемые новые параметры `GET /api/products`:

- `radius=17.5` при явном `kind=tyre|wheel`;
- `tyre_size=195/70R17.5` — точное сравнение с `size_key`, только для шин;
- для дисков выбранный размер — `radius=17.5&width=6.75` (width уже есть).

Старый `size` продолжает точное сравнение исходного текста. `rim_diameter`
и `diameter` сохраняются; не менять их смысл. Старые и новые ограничения
сочетаются через AND, противоречивый допустимый подбор даёт пустую выдачу.
Неизвестные/повторные параметры, неверная категория, NaN/Infinity и невалидные
числа — 400. Лимиты длины/пагинации и параметризация SQL сохраняются.
Старый URL диаметра переводить в новый выбор только при эквивалентности;
сырой size не заменять на канонический, если это расширяет исходную выдачу.

Добавить публичный `GET /api/products/selection?kind=tyre&radius=17.5&…`:
отдельный контракт зависимого подбора, не ломать прежние `/filters`.
Принимает выбранные фильтры без sort/pagination; обязательна категория.
Ответ содержит `radii` и `sizes`, у варианта — машинное значение, подпись,
`product_count` и `unit_count`. Список размеров пуст без диаметра.
Числа вариантов сортируются численно, размеры шин — по числовым компонентам
с учётом единиц, а не лексикографически по исходной строке.

- Радиусы учитывают общие/дополнительные фильтры, но исключают выбранные
  radius и размер (включая их старые эквиваленты), чтобы оставались альтернативы.
- Размеры учитывают выбранный radius и дополнительные фильтры, исключая
  выбранный полный размер шины или width диска. Точно описать набор исключаемых
  ключей в контракте/тестах, включая legacy size/diameter/rim_diameter.
- Агрегация SQL `GROUP BY` по таблице нужного типа с JOIN products;
  не читать весь каталог в Go и не строить один запрос на каждую плитку.
- Только опубликованные товары. Нулевой stock не скрывается автоматически:
  вариант может показывать 0 шт и открывать соответствующие карточки;
  `in_stock=true` исключает такие товары. Отсутствующий выбранный вариант
  сохранить в UI с нулём и возможностью снятия, без автоматической смены выбора.
- `unit_count = SUM(stock::bigint * units_per_sale::bigint)`; каст до умножения,
  проверить границы типа/JSON. `product_count = COUNT(*)`; `total` списка
  остаётся количеством карточек. Комплект не превращается в штучную продажу.
- Радиусы и размеры ответа читать из одного согласованного снимка SQL;
  отдельный запрос выдачи может увидеть более свежий stock. Счётчик не резервирует
  товар, покупка сохраняет существующую проверку цены/остатка.

Публичный DTO можно аддитивно дополнить `radius`/`size_key`, сохранив прежние
details. Проверить совместимость snapshot schema_version 1 и его потребителей;
не менять версию без необходимости. Новые URL включить в noindex/canonical
политику фильтров; не генерировать SSG всех комбинаций. Первоначальный HTML
и гидратация должны совпадать, затем подбор обновляется через API.

## Скорость и индексы

Начальные кандидаты B-tree в новой миграции:

- `tyre_specs (radius, size_key, product_id)`;
- `wheel_specs (radius, width_inches, product_id)`.

Первый ключ поддерживает подбор по одному диаметру, следующие — по размеру.
Индексы расположены на физических таблицах; не фильтровать через regex при
каждом SELECT и не применять функции к индексированному столбцу в WHERE.
Для выбранной категории предпочтителен JOIN соответствующей specs-таблицы;
проверить, что общая проекция не мешает использованию индекса.

Перед фиксацией набора снять baseline и `EXPLAIN (ANALYZE, BUFFERS)` на
синтетических 2 000 и 20 000 товарах: популярные/редкие диаметры, перекос
размеров, скрытые/нулевые товары, комплекты, фотографии, дополнительные фильтры.
Сравнить до/после `ANALYZE`: список, отдельный COUNT, оба набора счётчиков,
первая/глубокая страницы, явная сортировка цен и default «с фото первыми».
Индекс размера не устраняет автоматически сортировку по наличию фотографий.

По планам запросов оценить частичный индекс products для опубликованной
категории и отдельный индекс size_key для запроса размера без radius.
Не добавлять индексы на все возможные сочетания PCD/ET/DIA и не дублировать
уже существующий индекс product_images с ведущим product_id.
На маленькой таблице Seq Scan может быть быстрее; не отключать его ради теста.

Предлагаемый локальный бюджет после прогрева на 20 000 товаров при 10
одновременных клиентах: p95 <= 50 мс на SQL-операцию, p95 <= 150 мс на
каждый endpoint списка/подбора целиком, без внешней сети. Зафиксировать CPU/RAM,
pool, объём данных, число повторов, p50/p95/p99, ошибки, холодные и тёплые замеры.
При превышении сначала исследовать план/COUNT/сортировку/ожидание pool.
Это критерий будущей проверки, не достигнутый результат и не обещание latency
Cloud Run/Aiven. Измерить также стоимость записи и размеры индексов.
