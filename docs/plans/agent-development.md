# Переход к разработке агентами из Dev Containers

Статус: частичная реализация, 2026-10-17. [Основной roadmap](../../PLANS.md).
Созданы compose.agent.yaml, bootstrap и отдельные volumes tools/Codex.
Версия CLI закреплена в проекте. Инструкция запуска — в [README](../../README.md).
Login и взаимодействие с моделью выполняет пользователь; полноценное подключение
VS Code к agent с проверкой credential forwarding остаётся отдельной задачей.

## Проверка bootstrap и состояния 2026-10-17

- Собран agent image; четыре инструмента установлены в новый agent_tools по lockfile.
- После force-recreate bootstrap завершился без переустановки; контрольный файл
  в agent_codex сохранился, затем удалён. Реальные credentials не читались.
- Проверены версии CLI/toolchain, права vscode:700, read-only `.local`,
  отсутствие Docker/SSH sockets и sudo-разрешения vscode, git status, SELECT 1.
- При отсутствии проектных файлов bootstrap завершается ошибкой без ready-маркера.
- Авторизация и запрос к модели ещё не проверены. Сеть без allowlist; подключение
  VS Code непосредственно к агенту остаётся будущей задачей.

## Что уже подтверждено

- Пользователь открыл проект через Dev Containers.
- `docker --context lighter compose ps`: dev запущен, postgres healthy.
- `docker --context lighter compose exec -T dev bash -lc 'uname -s; id -un; pwd'`:
  Linux, vscode, /workspace.
- `mise exec -- go version`, `mise exec -- bun --version`,
  `mise exec -- node --version` внутри dev работают и соответствуют `mise.lock`.
- Lockfile содержит платформы Linux ARM64/x64; установка проверена на ARM64.
  x64 в этом окружении не проверялся.

## Как пользователь работает с основной машины

```text
Mac: VS Code (окно и управление) ── Dev Containers ── Linux: Codex CLI
Mac: терминал управления ───────── Docker Compose ── agent/dev/postgres
Mac: браузер ───────────────────── localhost port ── frontend/API
```

Начальный интерфейс общения с агентом — встроенный терминал VS Code,
открытого в нужном контейнере. После установки CLI пользователь вводит
`cd /workspace` и `codex`, общается с ним в терминале. Чтение/редактирование кода
и команды CLI происходят в этом контейнере. Окно VS Code остаётся на Mac.
Можно подключиться из терминала Mac через `docker compose exec`, но Compose
должен указывать на правильный проект/сервис/рабочую копию.

Открытие Dev Container само по себе не переносит текущую сессию агента на хосте
в Linux. Новому CLI-сеансу передать задачу и пути AGENTS.md/PLANS.md; история
этого чата автоматически ему не обещается. Постоянный контекст хранится в проекте.

Просмотр приложения — браузер Mac через проверенный port forwarding VS Code
или публикацию порта на `127.0.0.1`. Порты назначить после выбора frontend/API.
UI в браузере подключается к доступному с Mac API URL или через proxy;
Compose-имена вроде `postgres` предназначены для контейнерной сети.
Сам PostgreSQL наружу публиковать для этого не требуется.

## Следующая реализационная задача: готовность одного агента

1. **Исходники и Git.** Git инициализирован, `.local/` исключена из Git.
   `.dockerignore` по указанию пользователя не меняется. Проверить список файлов перед первым
   коммитом. Сохранить планы, окружение и lockfile; реальные исходники не добавлять.
2. **Bootstrap.** Создать повторяемую установку `mise install --locked`,
   запускать её при создании среды и проверять после пересоздания.
   Установка проектных инструментов выполняется в Linux. Не регенерировать
   lockfile при каждом запуске. Не объявлять фиктивные test/lint/build успешными,
   пока приложение не создано.
3. **Codex.** Выбрать и зафиксировать версию CLI в проектном toolchain;
   предусмотреть доступность CLI и в неинтерактивных процессах (`mise exec/run`
   или корректный PATH). Проверить `codex --version` после пересоздания.
4. **Профиль агента.** Подготовить отдельную конфигурацию Dev Containers для
   agent service на общей базе инструментов. Один агент и одна рабочая копия
   на первом этапе; исходники заказчика — read-only. Убрать passwordless sudo,
   не передавать SSH agent, Git credential helper хоста, home и Docker socket.
   Применить non-root, cap_drop ALL, no-new-privileges и лимиты ресурсов.
   Проверить фактический запуск/доступы, включая настройки VS Code, а не только YAML.
5. **Sandbox и сеть.** Проверить совместимость sandbox выбранного Codex с
   контейнером. Не решать ошибки добавлением privileged или Docker socket.
   Если внешняя граница — контейнер, её права и сетевые ограничения должны
   быть явно проверены до отключения внутренней sandbox-защиты. Для установки
   зависимостей и работы модели предусмотреть нужные сетевые направления;
   одни cap_drop/no-new-privileges исходящую сеть не ограничивают.
6. **AI-login.** Выполнить интерактивную авторизацию CLI внутри контейнера.
   При необходимости использовать поддерживаемый установленной версией способ
   device login/браузерного входа. Сохранять только нужное состояние CLI в
   отдельном приватном volume; не монтировать целиком `~/.codex` с Mac и не
   помещать ключи в Git/образ/логи. Определить повторный вход и удаление состояния.
   Credential, доступный процессу CLI в контейнере, не считать недоступным
   другим процессам того же пользователя; это отдельная граница доверия.
7. **Локальные сервисы.** Проверить `SELECT 1` и persistence PostgreSQL,
   определить отдельную test DB/роль, безопасный reset только тестовых данных.
8. **Приёмка.** Пересоздать окружение и пройти проверки ниже; заполнить README
   реальными командами и обновить статусы PLANS.md. Затем дать первую задачу
   по аудиту данных, а не весь магазин одним промптом.

Порядок профилей: нынешний dev служит для настройки, целевой agent используется
для автономной работы с меньшими доступами. Контейнерный CLI пользователь
может контролировать из окна VS Code на основной машине.

## Проверки готовности

- Чистая установка по lockfile и запуск CLI проходят в Linux.
- После перезапуска доступны рабочие файлы и ожидаемое состояние CLI;
  после пересоздания инструменты восстанавливаются bootstrap-командой.
- Контейнер агента не видит личные credentials/SSH socket/Docker socket;
  не может изменять исходные XLSX/HTML/фото через альтернативный mount.
- Нужные сеть и БД доступны; есть понятная диагностика отказа.
- `git status`/`git diff` работают в рабочей копии, `.local` исключена из Git.
- Пользователь запускает CLI, ставит задачу, видит изменения и может остановить
  его через Ctrl+C; остановка контейнеров выполняется с хоста.
- Приложение, когда появится, открывается в браузере Mac, а тесты идут в Linux.
- Push выполняется под контролем пользователя; агент не получает GitHub токен.

## Первый рабочий цикл

После готовности среды задача агенту:

> Прочитай AGENTS.md, PLANS.md и docs/plans/catalog-materials.md. Выполни только
> аудит XLSX и связей с фотографиями на доступных read-only исходниках.
> Подготовь словарь полей, отчёт о несоответствиях и синтетический пример.
> Сохрани реальные значения отчёта вне Git. Исходники не меняй.
> Пока не реализуй приложение и не конвертируй изображения.
> Запиши выполненные проверки и оставшиеся вопросы в план.

Результат пользователь проверяет в diff и отчёте, затем выбирает следующую
небольшую задачу. Для кода критерии приёмки должны предшествовать реализации;
CI и локальные команды используют одинаковые проверки.

## Параллельная работа — после первого успешного цикла

- Одна независимая задача, изменяющая код → одна ветка/worktree → один контейнер.
  Образ общий, рабочие каталоги разные. Несколько контейнеров с одним writable
  mount не дают изоляции исходников.
- Реализовать launcher на хосте: создаёт worktree и уникальное имя Compose
  project, запускает контейнер с нужными mounts, затем убирает ресурсы задачи.
  Docker socket агенту не требуется. Перекрытие задач согласовывать до запуска.
- Проверить связь worktree с общим Git directory и пути внутри/снаружи
  контейнера. Нельзя предполагать, что mount только worktree достаточен.
  Worktrees разделяют Git metadata; если требуется более строгая изоляция,
  предложить отдельные clones как отдельное архитектурное решение.
- Отдельное изменяемое состояние тестов: DB/схема и роль, порты, рабочие
  outputs. Проверить, что reset одной задачи не затрагивает другую.
- Текущий `shutdownAction: stopCompose` учитывать: остановка окна не должна
  останавливать окружения других задач. Изолировать Compose projects и описать
  жизненный цикл общей БД, если она используется совместно.
- Read-only входные материалы можно разделять; изменяемые кеши/outputs и
  состояние аутентификации не разделять без явной необходимости.
- Сначала проверить два независимых задания; review, merge и итоговые тесты
  выполнять последовательно. Параллельность сама по себе не цель.
