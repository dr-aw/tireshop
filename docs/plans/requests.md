# Первый срез: заявка и админка

Статус: оформление и админка реализованы, 2026-10-28. [Основной план](../../PLANS.md).
Границы сервисов и правила цены — в [ADR](../decisions/0001-catalog-and-requests.md).
Реализованы правила заявки и PostgreSQL-хранение создания/повторов;
HTTP API и форма используют синтетические товары. Админка, история и списание
реализованы; актуальная проверка — в [плане админки](administrator.md).
Ниже сохранены этапы и обсуждения первого среза.

## Первый код без инфраструктуры

По запросу пользователя начать реализацию: создать один Go-модуль и пакет
internal/requests с расчётом суммы/снимком позиций и правилами смены статуса.
Сервисы остаются разделёнными по принятому ADR; пакет принадлежит сервису заявок.
Пока без HTTP, БД, миграций и внешних зависимостей. Проверки: изменения цены,
невалидные позиции, переполнение/границы JSON-чисел, независимость снимка от каталога,
все переходы статусов и обязательный комментарий при отмене, включая после доставки.
Mise-задачи test/lint/build добавлены для фактически существующего Go-кода.
README отличает сборку пакета от запуска работающего сервиса.

Проверено: mise run test (go test -race), mise run lint (vet/gofmt), mise run build.
Расчёт возвращает полный актуальный снимок при изменении цены; при остальных
ошибках частичного результата нет. Матрица тестов проверяет все переходы статусов,
включая запрет выхода из отменённого состояния и пробельный комментарий отмены.
Этот первый шаг не проверял БД/HTTP. Результаты следующего слоя приведены ниже.

## Подтверждено пользователем

- Одна заявка на всю корзину: одна или несколько товарных позиций.
  Уточнение пользователя снимает первоначальное ограничение одной позицией.
- Валюта всегда RUB; цены и суммы — целые рубли, без копеек.
  Цена за одну шину/диск, количество — целое положительное число штук.
- Покупатель добавляет товар в корзину и оформляет позже либо использует
  «Купить сейчас» для быстрого создания заявки.
- В обоих сценариях перед отправкой указывает имя и телефон и явно подтверждает
  оформление; комментарий необязателен. «Купить сейчас» обходит корзину,
  но не ввод контактов и подтверждение.
- Данные заявки: товар, сумма, имя, телефон, комментарий. Backend рассчитывает
  сумму, проверяет цену и сохраняет исторический снимок товара.
- Только администратор видит список/детали заявок и вручную меняет статус.
  Кабинета покупателя и просмотра статуса нет; сотрудник связывается с ним сам.
- Нет онлайн-оплаты и автоматического резервирования.
- Статусы: «Создано», «Доставка», «Доставлено», «Отменено».
- Основной путь: «Создано» → «Доставка» → «Доставлено»; отмена разрешена
  из каждого из этих состояний, всегда с обязательным комментарием администратора.

## Защита админки — принято

Пользователь согласовал собственный вход без готовых провайдеров.
Обоснование и граница отказа — в [ADR](../decisions/0002-admin-auth.md).

Отдельные учётные записи сотрудников
без публичной регистрации, пароль с Argon2id и серверные сессии в PostgreSQL.
MFA исключена из первой версии по уточнению пользователя.
В браузере только случайный идентификатор сессии в Secure/HttpOnly/SameSite cookie;
проверка роли admin на каждом защищённом API-запросе, запрет по умолчанию.
Нужны HTTPS, CSRF-защита изменений, ограничение попыток входа, сроки сессий,
отзыв при выходе/блокировке, безопасное создание и восстановление учётной записи.
Не отображать комментарии покупателя как HTML; журналировать смену статуса
без паролей и токенов. Публичное создание заявки требует собственной валидации
и ограничений частоты запросов.

Отдельные БД/сервис авторизации, Redis, JWT и внешний OIDC-провайдер не нужны
для принятой схемы. Принят срок сессии 72 часа от входа без продления активностью;
восстановление — вручную техническим администратором с доступом к БД и отзывом
старых сессий. До реализации описать процедуры создания
и восстановления доступа; криптографию выполнять готовыми библиотеками.

Основания для обсуждения: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html),
[Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## Шаги и проверка

Выполненный участок 2026-10-27 — HTTP и первая форма:

1. Сохранить пользовательские правки json/v2, проверить совместимость старых
   отпечатков; не менять смысл уже сохранённых ключей при смене сериализатора.
2. Добавить отдельные LOGIN/секреты для каталога и заявок, без административных
   credentials у API. Compose управляет пользователь с хоста.
3. Добавить main.go для двух сервисов, JSON DTO, список/детали товаров и POST заявки,
   лимит тела, deadlines, корректное завершение, health/readiness и ограничение нагрузки.
4. Создать React/TypeScript/Vite UI по бело-красным референсам .local: товары,
   количество, контакты, подтверждение. Сохранять попытку перед отправкой;
   при неопределённом результате повторять прежние ключ/тело; новые цены подтверждать
   новым ключом. Никакого публичного чтения заявок или временно открытой админки.
5. Добавить синтетическое наполнение отдельной dev-командой. Проверить сквозной
   сценарий интеграционно; новые unit-тесты только при содержательной необходимости.
   Комментарии к функциям и сложным веткам писать на английском.

Публикация, полноценный каталог/фото, админка и CI остаются следующими участками.

Завершённый участок — PostgreSQL:

1. Проверить уже добавленный пользователем goose через mise install --locked;
   добавить pgx как Go-зависимость с go.sum.
2. Создать отдельные SQL-миграции каталога (товары и view) и заявок (заявка,
   позиции, ключ/отпечаток/результат). Схемами владеет роль миграций, runtime-роли
   получают только нужные права; имена ролей привязаны к dev/test DB.
3. Написать создание заявки: нормализация ввода → захват уникального ключа →
   одна выборка каталога → проверка цены → запись заявки и позиций → результат → commit.
   Конфликты цены/доступности сохраняются как результат ключа; неожиданные ошибки
   откатывают транзакцию. Повтор с другим телом возвращает конфликт.
4. В отдельной временной БД проверить миграции/повтор up, права, конкурентные
   повторы, другое тело с тем же ключом, откат при ошибке и исторический снимок.
5. Обновить README и разобрать с пользователем созданные файлы. HTTP, login,
   сохранение смены статусов и frontend остаются следующим участком.

Существующий контракт конкретизируется: IDs и ключ — UUID, строки контактов
обрезаются по краям, позиции сортируются по ID для отпечатка. Перестановка позиций
не создаёт конфликт ключа; изменение контактов/количества/показанной цены создаёт.
Границы полей и корзины фиксируются в коде и контракте до запуска тестов.

- [ ] Согласовать оставшиеся вопросы контракта и детали принятой защиты.
- [ ] После допуска окружения создать каркас, миграции/роли и dev/test fixtures.
- [ ] Реализовать оформление, затем защищённые список/детали и смену статуса.
- [ ] Проверить сквозной сценарий, добавить реальные задачи mise и CI,
   сборки runtime images и инструкции запуска.

Критерии: изменившаяся цена требует повторного подтверждения; сетевой повтор
не создаёт дубль; заявка сохраняется атомарно; изменение товара не меняет историю;
аноним не читает заявки и не меняет статусы даже прямым API-запросом;
истёкшая/отозванная сессия не работает, CSRF-запрос не меняет данные.
Проверить безопасное отображение пользовательского комментария в админке.
При недоступности БД защищённые операции отклоняются как временно недоступные,
без обхода проверки сессии; неверный пароль не создаёт сессию.
