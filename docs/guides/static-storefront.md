# Сборка и публикация SSG

Витрина остаётся на Render Static Site. Решение и ограничения —
[ADR 0007](../decisions/0007-static-storefront.md).

## Локально в Linux dev container

`mise run dev` сохраняет Vite/API workflow. Он не проверяет production HTML.
Для готового HTML:

```bash
mise run frontend:build
mise run test:ssg
mise exec -- bun frontend/scripts/preview.ts
```

Без настроек сборка использует только синтетический каталог из 30 товаров.
Preview доступен на 127.0.0.1:5175, при необходимости открыть через VS Code Ports.
Он возвращает настоящие 404; Vite SPA fallback для этой проверки не подходит.
Для локального API перед сборкой задать `SSG_CATALOG_URL` с адресом
`http://127.0.0.1:8081/api/products/snapshot`. Можно передать `SSG_SNAPSHOT_FILE`
с публичным JSON; этот файл не коммитить. Не задавать оба источника одновременно.
`SITE_ORIGIN` задаёт origin canonical/sitemap, по умолчанию локальный адрес.

Сборка сначала проверяет снимок, пишет `frontend/dist-next`, затем заменяет dist.
Ошибка сохраняет предыдущий dist. `publication.json` содержит версию снимка,
время и SHA кода; персональных данных там нет. Ответ API ограничен 32 MiB,
timeout 20 секунд. Если версия изменилась до завершения сборки, публикация
отменяется и нужна повторная попытка. Пустой каталог разрешается только явным
`SSG_ALLOW_EMPTY=true`, чтобы сбой экспорта не очистил магазин.

## Render: последовательность перехода

1. Опубликовать новую версию catalog API с `/api/products/snapshot`.
2. В Static Site задать `SSG_CATALOG_URL` (прямой HTTPS URL catalog API) и
   `SITE_ORIGIN` (выбранный публичный origin). Секреты PostgreSQL не нужны.
   Build command остаётся `bash scripts/render-static-build.sh`, каталог —
   `frontend/dist`. Auto-Deploy оставить выключенным. Render-сборка требует
   явные настройки и не должна публиковать синтетический каталог.
3. Вручную собрать проверенный commit. Сначала проверить страницы и медиа.
4. Удалить rewrite `/products/* → /index.html`. Карточки собираются как
   `products/{uuid}.html`; проверить extensionless URL и canonical на Render.
   Если хост не разрешает `.html` автоматически, нужен точный rewrite пути
   на существующий файл, который не превращает отсутствующий товар в HTTP 200.
   `/administrator` и `/administrator/` направить на `/administrator.html`.
   API и `/media/*` сохранить отдельно; глобальный SPA fallback не добавлять.
5. Проверить `/about/`, `/contacts/`, `/blog/`, `/cart/`, категории, вторую страницу
   и прямой вход на товар. У неизвестного адреса должен быть HTTP 404.
   Сгенерирован `404.html`, но его автоматическое использование Render пока
   не подтверждено внешней проверкой. Не подменять проверку локальным сервером
   и не делать rewrite на 404.html со статусом 200. Если custom error page
   недоступна штатно, оставить корректный статус и отдельно выбрать механизм
   брендированной страницы; не добавлять SSR только ради этого без решения.
6. Проверить покупку, смену цены/остатка и `publication.json`, затем обновления.

## Периодическая публикация

До успешного ручного rollout расписание не включать. Рекомендуемый начальный
интервал — 30 минут, до 48 сборок в сутки; это не обещание свежести ровно 30 минут.
В Render учитываются pipeline minutes, требуется проверить лимиты аккаунта.

Render deploy hook поддерживает параметр `ref` с полным SHA commit:
[документация](https://render.com/docs/deploy-hooks). Для расписания использовать
закреплённый успешно проверенный SHA, не текущий main. После релиза кода обновлять
этот SHA вместе с настройкой расписания. URL hook — секрет; не хранить его в
frontend/Git, не выводить в логах или аргументах команд.

Подготовлен GitHub Actions workflow (см. ниже). Он должен ожидать завершения
публикации (одной блокировки HTTP вызова hook недостаточно), объединять пропущенные
запуски, не допускать параллельных deploy и сообщать о сбое. При несовпадении
снимка повторить сборку с ограниченным числом попыток. Пока такой планировщик
не подключён, публикация ручная; сайт и API работают независимо от него.
Настройки аккаунта и активация расписания этим изменением не выполняются.

Откат: вернуть предыдущий статический deploy, совместимый с текущим API.
Не откатывать схему БД. После отката проверить, что расписание не переопубликует
отменённую версию. Render выполняет атомарный deploy и инвалидацию CDN:
[Static Sites](https://render.com/docs/static-sites).

## Контент

«О нас»/«Контакты» — `frontend/src/information.tsx`, текст из бизнес-PDF.
Логотип и изображения не обновлялись. Мессенджеры ожидают подтверждённых URL.
Блог пока показывает подготовку материалов. XLSX содержит семь черновиков:
сравнения шин без конкретных ссылок на тесты, рекомендации по возрасту/износу,
маркировку и новости о пошлинах/моделях. Они требуют редакционной проверки;
фиктивные даты и просмотры из макета не перенесены. Редактор/CMS не добавлялись.

### Подготовленный workflow обновления

`.github/workflows/static-content.yml` подготовлен с расписанием в 17-ю и 47-ю
минуту часа и ручным запуском. По умолчанию job пропускается: требуется
repository variable `SSG_REFRESH_ENABLED=true`. До rollout её не включать.
Другие variables: `RENDER_STATIC_SERVICE_ID` и полный `RENDER_CONTENT_COMMIT`
(40 символов, SHA уже работающей проверенной версии). Secret `RENDER_API_TOKEN`
нужен только этому job, не сборке frontend. Настройки репозитория агент не менял.

Используется API вместо hook, чтобы дождаться завершения deploy. Скрипт
`scripts/render-content-deploy.mjs` отказывается публиковать, если закреплённый SHA
не совпадает с live, пропускает запуск при незавершённом deploy, отправляет один
POST и ждёт до 20 минут. Сбой отмечается failed job; следующий запуск проверяет
уже существующие deploy перед новой попыткой. Token/ответы API не печатаются.

GitHub concurrency сериализует эти jobs. Перед ручным релизом/откатом отключить
расписание и дождаться текущего deploy: блокировка Actions не блокирует действия
в Render Dashboard. После релиза обновить закреплённый SHA и включить расписание.
Автоматизация проверена offline с поддельными ответами API; реальные права,
формат ответов аккаунта и доставка по расписанию требуют проверки после rollout.
[Контракт запуска Render API](https://api-docs.render.com/reference/create-deploy).

## Прямые фотографии Google Storage

В Render → Static Site → Environment добавить публичную переменную:

```text
VITE_MEDIA_BASE_URL=https://storage.googleapis.com/tireshop-513806-product-media
```

Это адрес bucket БЕЗ `/media` в конце. Затем опубликовать commit с поддержкой
этой настройки: она встраивается при сборке, нужен rebuild, не простой restart.
SSG HTML, Product JSON-LD, галерея, ссылка на оригинал и фото корзины/админки
получают прямой URL Google Storage. API и БД продолжают хранить `/media/...`.
Старые локальные записи корзины преобразуются при отображении.

Новый backend, секреты, изменения Terraform/БД и повторная загрузка файлов
не требуются. Bucket уже публичный; для обычных img не требуется настройка CORS.
Без переменной сохраняется локальная выдача. Неверный HTTPS base прерывает сборку.

После deploy в DevTools → Network при переключении фото запрос должен идти на
`storage.googleapis.com/tireshop-513806-product-media/media/...`, а не домен Render.
Проверить карточку, корзину и оригинал фото. Старый `/media/*` rewrite можно
сохранить для старых вкладок и прямых ссылок: новые img его не используют.
Этот этап убирает промежуточный Render, но не добавляет предзагрузку/новые размеры.
