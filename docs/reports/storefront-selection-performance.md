# Измерения подбора каталога

2026-11-10, локальная PostgreSQL, только синтетическая отдельная test DB.
Повторение: `mise run test:selection-performance` внутри Linux container.
Задача создаёт/удаляет свою БД, сначала выполняет integration/race,
затем измерения без race detector. Она не меняет dev или production.

Приложение: cgroup 2 CPU, 4 GiB, GOMAXPROCS=2, pool=8; PostgreSQL — соседний
локальный контейнер. 2 000 / 20 000 товаров, 75% шин, 25% дисков, неравномерные
диаметры/размеры, скрытые позиции, нулевые остатки, комплекты, фотографии.
Это не модель внешней сети, cold start Cloud Run или ресурсов Aiven.

## HTTP после оптимизации

Для каждого endpoint — 300 запросов, 10 параллельных клиентов, ошибок 0.
Время включает чтение полного HTTP-ответа, ожидание pool и сериализацию.

| Товаров | Endpoint | p50, мс | p95, мс | p99, мс |
| --- | --- | --- | --- | --- |
| 2 000 | Список шин R17.5 | 3.15 | 5.14 | 10.33 |
| 2 000 | Подбор шин R17.5 | 1.89 | 3.17 | 4.16 |
| 2 000 | Подбор дисков R17.5 + PCD | 3.42 | 5.60 | 6.17 |
| 20 000 | Список шин R17.5 | 21.88 | 30.01 | 32.84 |
| 20 000 | Подбор шин R17.5 | 23.81 | 34.87 | 40.99 |
| 20 000 | Подбор дисков R17.5 + PCD | 30.48 | 41.22 | 44.51 |

Плановый локальный бюджет p95 <= 150 мс выполнен.
До изменения порядка запроса список на 20 000 товарах имел p95 233.12 мс
при тех же 10 клиентах. JSON характеристик вычислялся для всей выборки до
LIMIT. Теперь MATERIALIZED CTE выбирает ID страницы; характеристики и фото
читаются для страницы. Сортировка «с фото первыми», цена, UUID и OFFSET сохранены.

## SQL и индексы

Для каждого сценария снят EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON), затем
20 последовательных измерений с чтением ответа. Проверены COUNT, страница
и selection: популярный/менее частый диаметр, размер, OFFSET=960, сортировка
ценой, диски с width/PCD/in_stock. При 20 000 товарах p95 после оптимизации
на проверенных сценариях <= 10.08 мс, бюджет <= 50 мс выполнен.

Сравнение без/с двумя индексами сделано в той же test DB без отключения Seq Scan.
Индекс шин используется в планах более избирательного подбора. Для широких
агрегаций и некоторых выборок дисков планировщик выбирает последовательное
чтение: суммарные счётчики требуют просмотреть подходящие товары. Индекс не
заменяет эту работу и сортировку по наличию фотографий.

Финальные индексы:

- `tyre_specs(radius, size_key, product_id)`: 901 120 байт на 15 000 шин.
- `wheel_specs(radius, width_inches, product_id)`: 270 336 байт на 5 000 дисков.

Обновление 1 000 размеров с generated columns и индексом — 44.07 мс.
Дополнительные индексы products/size_key/PCD не добавлены: текущие бюджеты
выполнены, основные новые запросы используют пару radius + размер.
Запросы legacy size без radius функционально поддерживаются, но отдельное
нагрузочное измерение для них и индекс под них в этот результат не входят.

Первый EXPLAIN каждого сценария фиксирует первый запуск, но это **не** измерение
холодного дискового кеша: OS/PostgreSQL caches не очищались, общий сервер не
перезапускался. Тёплые результаты и первый запуск нельзя выдавать за cold-start
SLA. Планы и исходные логи доступны локально в
`.tmp/catalog-selection/performance-page.log`, прежний запрос —
`.tmp/catalog-selection/performance-before-page.log`; они не коммитятся.
